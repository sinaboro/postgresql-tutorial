# 13장 ∙ 인덱스와 실행 계획

## 학습 목표

- 인덱스가 검색을 빠르게 하는 원리(B-tree)와 그 비용을 설명할 수 있다.
- EXPLAIN / EXPLAIN ANALYZE 로 실행 계획을 읽고 Seq Scan, Index Scan, Bitmap Scan 을 구분할 수 있다.
- 단일·복합·표현식·부분 인덱스를 상황에 맞게 만들 수 있다.
- 인덱스를 쓰지 못하는 쿼리 패턴을 알아보고 고칠 수 있다.

예제 파일: `examples/13_index_explain.sql` (100만 건 생성에 수 초~수십 초 소요)

## 인덱스의 원리

인덱스는 책 뒤의 **찾아보기**와 같습니다. 컬럼 값을 정렬된 트리(B-tree)로 따로 저장해 두고, 값을 찾을 때 트리를 따라 내려가 해당 행의 위치로 바로 갑니다. 100만 건에서 한 건을 찾을 때 전체를 읽는 대신 3~4개 페이지만 읽습니다.

| 장점 | 비용 |
|---|---|
| WHERE, JOIN, ORDER BY 가 빨라짐 | 디스크 공간 (13-09 에서 크기 확인) |
| UNIQUE 제약의 검사 수단 | INSERT/UPDATE/DELETE 때마다 인덱스도 수정 → 쓰기 느려짐 |
| | 많이 만들수록 관리 부담, 쓰이지 않는 인덱스는 순수 비용 |

PRIMARY KEY 와 UNIQUE 제약에는 인덱스가 **자동으로** 만들어지지만, 외래 키에는 만들어지지 **않습니다**(13-12).

## 실행 계획 읽기

`EXPLAIN 쿼리` 는 옵티마이저가 세운 계획을, `EXPLAIN ANALYZE 쿼리` 는 실제로 실행한 결과(실제 행 수, 시간)를 보여 줍니다. 교재은 숫자가 PC 마다 다른 cost·시간을 `COSTS OFF, TIMING OFF` 로 숨겼습니다. 직접 실행할 때는 옵션 없이 실행해 실제 시간도 확인해 보세요.

| 노드 | 의미 |
|---|---|
| `Seq Scan` | 테이블 전체를 처음부터 끝까지 읽음 |
| `Index Scan` | 인덱스로 위치를 찾아 테이블 행을 하나씩 읽음 (소수 행) |
| `Index Only Scan` | 인덱스만 읽고 끝 (필요한 컬럼이 모두 인덱스에 있을 때) |
| `Bitmap Index/Heap Scan` | 인덱스로 위치 목록을 만든 뒤 테이블을 페이지 순서대로 읽음 (중간 정도 행) |
| `Gather` + `Parallel ...` | 여러 프로세스가 나눠서 병렬 처리 |
| `Hash Join` / `Nested Loop` / `Merge Join` | 조인 방법 |

## 복합 인덱스

여러 컬럼을 묶은 인덱스는 **왼쪽 컬럼부터 정렬**되어 있습니다(전화번호부가 성 → 이름 순인 것과 같음). 그래서 `(status, order_date)` 인덱스는 `status` 조건이 있을 때 가장 효과적입니다.

@@ex 13-06

> [!NOTE] PostgreSQL 18 의 skip scan
> 13-06 두 번째 쿼리처럼 선두 컬럼(status) 조건이 없으면 17 이하 버전은 이 인덱스를 거의 활용하지 못하고 Seq Scan 을 택하는 경우가 많습니다. 18 부터는 선두 컬럼의 값 종류가 적을 때(여기서는 4가지) 값마다 건너뛰며 인덱스를 탐색하는 **skip scan** 이 추가되어 활용할 수 있게 되었습니다. 그래도 **자주 쓰는 조건 컬럼을 앞에** 두는 원칙은 그대로입니다.

복합 인덱스 컬럼 순서 원칙:

1. `=` 조건으로 자주 쓰는 컬럼을 앞에, 범위(`>`, `BETWEEN`) 조건 컬럼을 뒤에.
2. `(a, b)` 인덱스가 있으면 `a` 단독 인덱스는 대개 필요 없습니다.
3. ORDER BY 까지 인덱스 순서와 맞으면 정렬 작업도 생략됩니다(실습 문제 13-Q1).

## 인덱스를 쓰지 못하는 경우

@@ex 13-07

| 패턴 | 이유 | 해결 |
|---|---|---|
| `WHERE col + 0 = 5`, `WHERE lower(email) = ...` | 컬럼을 가공하면 인덱스의 정렬 순서와 달라짐 | 가공하지 않게 쿼리 수정, 또는 **표현식 인덱스** |
| `WHERE name LIKE '%노트북'` | 앞부분이 정해지지 않음 | pg_trgm GIN 인덱스(16장) |
| `WHERE price::text = '1000'` | 형변환 | 컬럼 타입에 맞는 값으로 비교 |
| 결과가 테이블의 상당 부분 | 인덱스로 하나씩 읽는 것보다 전체 읽기가 빠름 | 정상 (옵티마이저의 올바른 판단) |
| 통계가 오래됨 | 행 수 추정이 틀림 | `ANALYZE` (18장) |

## 인덱스 관리

@@ex 13-13

| 명령 | 용도 |
|---|---|
| `CREATE INDEX CONCURRENTLY ...` | 운영 중인 테이블에 쓰기를 막지 않고 인덱스 생성 |
| `DROP INDEX [CONCURRENTLY] 이름` | 인덱스 삭제 |
| `REINDEX INDEX 이름` | 부풀어 오른 인덱스 재생성 |
| `pg_stat_user_indexes.idx_scan` | 사용 횟수, 0 이면 삭제 후보 |

> [!QA] 자주 묻는 질문
> - **Q. 모든 컬럼에 인덱스를 만들면 좋지 않나요?** 쓰기가 느려지고 공간을 차지합니다. 실제로 느린 쿼리의 WHERE / JOIN / ORDER BY 컬럼을 근거로 만듭니다(18장 pg_stat_statements).
> - **Q. 인덱스를 만들었는데 안 쓰여요.** ① 컬럼을 가공했는지 ② 결과 행이 많은지 ③ `ANALYZE` 를 했는지 ④ 테이블이 작은지 순서로 확인합니다.

## 정리

- EXPLAIN 으로 확인하고, ANALYZE 로 실제를 확인한다. 추측하지 말고 측정한다.
- 복합 인덱스는 왼쪽 컬럼부터, 가공된 컬럼은 표현식 인덱스로.
- 외래 키 컬럼 인덱스는 직접 만든다.
