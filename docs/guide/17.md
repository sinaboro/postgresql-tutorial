# 17장 ∙ 사용자와 권한 - ROLE, GRANT, 행 수준 보안

## 학습 목표

- ROLE(사용자·그룹)을 만들고 로그인 권한과 그룹 상속을 설정할 수 있다.
- GRANT / REVOKE 로 스키마·테이블·컬럼 단위 권한을 관리할 수 있다.
- 최소 권한 원칙에 따라 읽기 전용 계정과 애플리케이션 계정을 설계할 수 있다.
- 행 수준 보안(RLS)으로 사용자마다 볼 수 있는 행을 제한할 수 있다.

예제 파일: `examples/17_security.sql` (superuser 로 실행. ROLE 은 서버 전체 객체)

## ROLE

PostgreSQL 은 사용자와 그룹을 구분하지 않고 모두 **ROLE** 입니다. `LOGIN` 속성이 있으면 사용자, 없으면 권한을 묶어 두는 그룹으로 씁니다. (`CREATE USER` 는 `CREATE ROLE ... LOGIN` 의 별칭입니다.)

| 속성 | 의미 |
|---|---|
| `LOGIN` / `NOLOGIN` | 접속 가능 여부 |
| `PASSWORD '...'` | 비밀번호 (scram-sha-256 으로 저장) |
| `SUPERUSER` | 모든 권한 (운영에서는 최소한으로) |
| `CREATEDB`, `CREATEROLE` | DB / 롤 생성 권한 |
| `CONNECTION LIMIT n` | 동시 접속 수 제한 |
| `VALID UNTIL '날짜'` | 비밀번호 만료일 |

## GRANT 와 REVOKE

객체를 만든 사람(소유자)과 superuser 외에는 **명시적으로 권한을 받아야** 접근할 수 있습니다. 테이블에 접근하려면 그 테이블이 있는 **스키마의 USAGE 권한도** 필요합니다.

| 대상 | 주요 권한 |
|---|---|
| DATABASE | `CONNECT`, `CREATE`, `TEMP` |
| SCHEMA | `USAGE`(안의 객체 접근), `CREATE`(객체 생성) |
| TABLE | `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES`, `TRIGGER` |
| 컬럼 | `SELECT (컬럼들)`, `UPDATE (컬럼들)` |
| SEQUENCE | `USAGE`, `SELECT`, `UPDATE` |
| FUNCTION | `EXECUTE` |

> `GRANT SELECT ON ALL TABLES` 는 **지금 있는 테이블**에만 적용됩니다. 앞으로 만들 테이블에도 자동으로 권한을 주려면 17-03 처럼 `ALTER DEFAULT PRIVILEGES` 를 함께 설정해야 합니다. “새로 만든 테이블이 분석 계정에서 안 보여요” 라는 문의의 단골 원인입니다.

> [!POINT] 최소 권한 원칙으로 계정 나누기
> 실무에서 권장하는 구성입니다.
> - `postgres`(superuser): DBA 만, 원격 접속 금지
> - `app_owner`: 테이블 소유자, 스키마 변경(마이그레이션)에만 사용
> - `app_user`: 애플리케이션 접속용, 필요한 테이블의 SELECT/INSERT/UPDATE/DELETE 만
> - `readonly` 그룹 → `analyst` 등 개인 계정: 분석·조회용
> 애플리케이션이 superuser 로 접속하면 SQL 인젝션(19장) 한 번에 DB 전체가 위험해집니다.

## 행 수준 보안 (Row Level Security)

RLS 는 테이블에 **정책(POLICY)** 을 걸어 사용자마다 보이는 행, 수정할 수 있는 행을 제한합니다. 멀티테넌트 SaaS(회사별 데이터 분리), 영업사원별 고객 관리 등에 씁니다.

```
ALTER TABLE 테이블 ENABLE ROW LEVEL SECURITY;
CREATE POLICY 정책명 ON 테이블
    FOR SELECT | INSERT | UPDATE | DELETE | ALL
    TO 롤                 -- 생략 시 모든 롤
    USING (보이는 행 조건)
    WITH CHECK (쓰는 행 조건);
```

> [!NOTE] RLS 의 예외
> 테이블 소유자와 superuser, `BYPASSRLS` 속성이 있는 롤에는 정책이 적용되지 않습니다(17-08 의 postgres 는 120건 전체). 소유자에게도 적용하려면 `ALTER TABLE ... FORCE ROW LEVEL SECURITY` 를 씁니다. 애플리케이션이 하나의 계정으로 접속하는 구조라면 `current_user` 대신 `SET app.user_id = '6'` 같은 설정값과 `current_setting('app.user_id')` 를 정책에 사용합니다.

## 접속 제어 - pg_hba.conf

누가 어디에서 어떤 방식으로 접속할 수 있는지는 데이터 디렉터리의 `pg_hba.conf` 파일이 정합니다(위에서부터 처음 일치하는 줄 적용). 파일 위치는 `SHOW hba_file;` 로 확인합니다. Docker 컨테이너에서는 `docker exec -it pg-shop bash` 로 들어가 편집합니다. 수정 후 `SELECT pg_reload_conf();` 로 반영합니다.

```
# TYPE  DATABASE  USER       ADDRESS          METHOD
local   all       postgres                    scram-sha-256
host    shop      app_user   10.0.1.0/24      scram-sha-256
host    shop      analyst    192.168.0.0/16   scram-sha-256
host    all       all        0.0.0.0/0        reject
```

> [!WARN] 보안 체크리스트
> - `trust` 인증은 로컬 실습 외에는 쓰지 않는다.
> - `listen_addresses` 와 방화벽으로 DB 포트(5432)를 인터넷에 직접 노출하지 않는다.
> - 비밀번호를 코드·깃 저장소에 넣지 않는다(19장의 환경변수 방식).
> - 민감 정보(비밀번호)는 해시로 저장한다(18장 pgcrypto `crypt`).

> [!QA] 자주 묻는 질문
> - **Q. 사용자를 지우려는데 오류가 나요.** 그 롤이 소유한 객체나 받은 권한이 남아 있으면 지울 수 없습니다. 17-09 처럼 `REASSIGN OWNED BY 롤 TO 다른롤; DROP OWNED BY 롤;` 후 `DROP ROLE` 합니다. 권한은 DB 마다 따로 있으므로 각 DB 에서 실행해야 합니다.

## 정리

- ROLE = 사용자 + 그룹. 그룹 롤에 권한을 주고 사용자를 그룹에 넣는다.
- 테이블 권한 + 스키마 USAGE, 앞으로의 객체는 DEFAULT PRIVILEGES.
- 행 단위 제한은 RLS, 접속 제한은 pg_hba.conf.
