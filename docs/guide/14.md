## 트랜잭션과 ACID

트랜잭션은 **“모두 성공하거나 모두 실패해야 하는 작업 묶음”** 입니다. 계좌 이체에서 출금만 되고 입금이 안 되면 안 됩니다.

| 속성 | 의미 | PostgreSQL 의 구현 |
|---|---|---|
| Atomicity (원자성) | 전부 반영되거나 전부 취소 | 실패 시 트랜잭션 전체 ROLLBACK |
| Consistency (일관성) | 제약 조건을 항상 만족 | CHECK, FK, UNIQUE 등 |
| Isolation (격리성) | 동시에 실행되는 트랜잭션끼리 간섭하지 않음 | MVCC + 격리 수준 + 잠금 |
| Durability (지속성) | COMMIT 된 결과는 장애 후에도 유지 | WAL(선행 기록 로그) |

psql 과 대부분의 도구는 **자동 커밋(autocommit)** 모드입니다. `BEGIN` 없이 실행한 문장은 각각 하나의 트랜잭션으로 즉시 커밋됩니다.

## MVCC - 읽기와 쓰기가 서로 막지 않는다

PostgreSQL 은 행을 수정할 때 덮어쓰지 않고 **새 버전을 추가**합니다(Multi-Version Concurrency Control). 각 버전에는 만든 트랜잭션 번호(`xmin`)와 지운 트랜잭션 번호(`xmax`)가 기록되고, 각 트랜잭션은 자신이 볼 수 있는 버전만 봅니다. 그래서 **읽기는 쓰기를 기다리지 않고, 쓰기도 읽기를 기다리지 않습니다.** 남은 옛 버전(dead tuple)은 VACUUM(18장)이 정리합니다.

xmin/xmax 의 숫자는 환경마다 다릅니다. UPDATE 후 1번 행의 `xmin` 이 바뀐 것(새 버전)을 보여 주는 것이 핵심입니다.

## 격리 수준

| 격리 수준 | Dirty Read | Non-repeatable Read | Phantom Read | 직렬화 이상 |
|---|---|---|---|---|
| READ UNCOMMITTED | (PostgreSQL 은 READ COMMITTED 로 동작) | 가능 | 가능 | 가능 |
| **READ COMMITTED (기본)** | 없음 | 가능 | 가능 | 가능 |
| REPEATABLE READ | 없음 | 없음 | 없음 (PostgreSQL) | 가능 |
| SERIALIZABLE | 없음 | 없음 | 없음 | 없음 |

- **READ COMMITTED**: 문장(SELECT)마다 그 시점에 커밋된 데이터를 봅니다. 같은 트랜잭션에서 두 번 읽으면 값이 다를 수 있습니다.
- **REPEATABLE READ**: 트랜잭션의 첫 문장 시점 스냅샷을 끝까지 봅니다. 다른 트랜잭션이 이미 고친 행을 수정하려 하면 `could not serialize access` 오류가 나고, 애플리케이션이 **재시도**해야 합니다.
- **SERIALIZABLE**: 트랜잭션들을 한 번에 하나씩 실행한 것과 같은 결과를 보장합니다. 충돌 시 오류 → 재시도.

### 두 세션 실습 (DBeaver 편집기 2개)

| 순서 | 세션 A | 세션 B |
|---|---|---|
| 1 | `BEGIN;` `SELECT balance FROM accounts WHERE account_id = 1;` → 현재 잔액 | |
| 2 | | `UPDATE accounts SET balance = 0 WHERE account_id = 1;` (자동 커밋) |
| 3 | `SELECT balance ...;` → **0** (READ COMMITTED) | |
| 4 | `COMMIT;` → 이번엔 `BEGIN ISOLATION LEVEL REPEATABLE READ;` 로 반복 | |
| 5 | 3단계에서 **처음 값 그대로** 보임 | |

## 잠금과 갱신 손실

MVCC 덕분에 읽기는 막히지 않지만, **같은 행을 동시에 수정**하면 나중 트랜잭션은 앞 트랜잭션이 끝날 때까지 기다립니다(행 잠금).

@@ex 14-08

> [!NOTE] 행 잠금은 pg_locks 에 보이지 않는다
> 14-08 에서 pg_locks 에는 테이블 수준의 `RowShareLock` 만 보입니다. PostgreSQL 은 행 잠금 정보를 행 자체(xmax)에 기록하므로 행 잠금이 아무리 많아도 메모리를 차지하지 않습니다. 다른 세션이 기다리는 중이라면 그 세션의 `transactionid` 잠금 대기가 pg_locks 에 나타납니다.

**갱신 손실(Lost Update)**: 두 세션이 같은 값(1000)을 읽고, 각자 계산해서(1000-300, 1000-200) 저장하면 먼저 저장한 결과가 사라집니다. 예방법은 세 가지입니다.

1. **원자적 UPDATE**: `SET balance = balance - 300` 처럼 DB 가 현재 값으로 계산 (14-09, 가장 간단)
2. **비관적 잠금**: `SELECT ... FOR UPDATE` 로 읽을 때 잠가 두기 (15장 `place_order` 함수)
3. **낙관적 잠금**: `version` 컬럼을 두고 `UPDATE ... WHERE id = ? AND version = ?` 의 결과 행 수가 0 이면 재시도

## 데드락

세션 A 가 1번 행을 잠그고 2번을 기다리는데, 세션 B 는 2번을 잠그고 1번을 기다리면 영원히 끝나지 않습니다. PostgreSQL 은 이를 감지(기본 1초, `deadlock_timeout`)해 한쪽을 `deadlock detected` 오류로 취소합니다.

| 순서 | 세션 A | 세션 B |
|---|---|---|
| 1 | `BEGIN; UPDATE accounts ... WHERE account_id = 1;` | |
| 2 | | `BEGIN; UPDATE accounts ... WHERE account_id = 2;` |
| 3 | `UPDATE ... WHERE account_id = 2;` → 대기 | |
| 4 | | `UPDATE ... WHERE account_id = 1;` → **deadlock detected** (취소됨) |
| 5 | B 가 취소되며 A 의 UPDATE 진행 → `COMMIT;` | `ROLLBACK;` |

> [!TIP] 데드락 예방
> - 여러 행을 잠글 때는 **항상 같은 순서**(예: id 오름차순)로 잠급니다.
> - 트랜잭션을 짧게 유지합니다. 트랜잭션 안에서 사용자 입력이나 외부 API 호출을 기다리지 않습니다.
> - `idle in transaction` 상태로 오래 남은 세션은 잠금을 붙잡고 있으므로 18장의 방법으로 찾아 정리합니다.

> [!QA] 예상 질문
> - **Q. 격리 수준을 무조건 SERIALIZABLE 로 하면 안전하지 않나요?** 안전하지만 충돌 시 오류가 자주 나고 모든 코드에 재시도 로직이 필요합니다. 대부분의 서비스는 기본값(READ COMMITTED) + 원자적 UPDATE / FOR UPDATE 로 충분합니다.
> - **Q. DDL 도 롤백되나요?** PostgreSQL 은 CREATE/ALTER/DROP TABLE 도 트랜잭션 안에서 롤백됩니다(일부 예외: CREATE DATABASE, CREATE INDEX CONCURRENTLY, VACUUM). 다른 DBMS 와 다른 큰 장점입니다.

## 정리

- 트랜잭션 안의 오류는 전체 취소. 부분 취소는 SAVEPOINT.
- MVCC: 읽기와 쓰기가 서로 막지 않는다. 같은 행 쓰기끼리만 기다린다.
- 갱신 손실은 원자적 UPDATE / FOR UPDATE / 버전 컬럼으로, 데드락은 일정한 잠금 순서로 예방.
